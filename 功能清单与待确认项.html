1. 项目概述

本系统是一套面向客户技术负责人的技术集成与需求调研演示原型，定位为「统一监控与岗位交接中心」。它把分散在 ERP、支付网关、结算、核心网络、堡垒机、IAM、TMS、ITSM、VMS、SCM、BI、WMS 等多个子系统中的健康度、异常与交接事项，汇聚到一个中心化大屏，并提供告警、存证、交接、权限等闭环管理能力。

技术栈 纯静态站点：HTML + CSS + 原生 JS，零依赖、零构建、离线可用
交付形态 双击 index.html 即可打开，或 python -m http.server
演示数据 全部为虚构样例，页面改动存于浏览器 LocalStorage，不触达生产
本清单依据项目源码（assets/js/* 与 README.md）逐页梳理，覆盖 7 个业务页面 + 公共引擎 + 邮件/关键词组件，共 10 个功能域、60+ 个功能点。

4.1 是否与对接系统形成「数据闭环」核心决策点

问题背景：本系统作为统一监控与岗位交接中心，会在发现问题时向各对接子系统（ERP、支付网关、VMS 等）的责任处室发出告警 / 警告。关键问题在于：告警发出之后，对方（子系统责任处室）的回复与处置反馈是否要回到本系统？

方案 A · 双向闭环（本系统内回复）

  • 对方在本系统内直接回复、认领、填写处置结果；
  • 本系统回写状态（待处置 → 处理中 → 已闭环），并留痕责任人与时间；
  • 告警流水、交接单、KPI 直接与处置状态联动；
  • 客户可在统一中心看到「谁、何时、怎么处置的」。
需要对接系统开放「回复 / 认领 / 处置反馈」写接口，对接系统需配合改造。

方案 B · 单向告警 + 原有系统处置（半闭环）

  • 本系统只发告警 / 通知，不接收回复；
  • 对方在其原有系统里查找、处置，并做交接回复；
  • 本系统不接收回复，仅做告警记录与交接单/日报追踪；
  • 「是否闭环」由本系统凭交接单或派单状态自行标记。
对接系统无需开放写接口，实施成本低、周期短，但闭环完整性依赖人工核对。
需要客户拍板 / 澄清的问题：
  • 告警发出后，对方是否需要在本系统内直接回复、认领并反馈处置结果（方案 A），还是可以接受在原有系统内查找、处置并做交接回复（方案 B）？
  • 若选方案 A，需要对接系统开放哪些写接口？（回复内容、处置状态、责任人、处置时间、备注等）
  • 「已闭环」的判定标准：以对方在本系统的回复为准，还是本系统自行标记即可？
  • 是否要求状态双向同步？例如原系统处置完成后，本系统能否自动感知并回写状态？
  • 若选方案 B，客户是否能接受「告警仅通知、闭环在原有系统完成、本系统凭交接单 / 日报做追踪」这一弱闭环模式？
影响评估：方案 A 的体验与数据完整性更好，但对接系统改造工作量、接口安全评估、实施周期显著更高；方案 B 落地最快、对既有系统零侵入。建议结合客户的对接系统开放程度与项目排期共同决定，必要时可采用「先 B 后 A」的渐进式路线。
